Getting started

MCP allows applications and AI clients to communicate with hardware through Serial Flux. The client launches the MCP executable automatically using STDIO. Do not start it manually. MCP Inspector is optional and intended for testing.

  1. Open a compatible Serial Flux release.
  2. Choose Tools → MCP Server Settings and enable MCP.
  3. Keep read-only mode unless a trusted client needs hardware control.
  4. Configure the client with the executable path below.

sf_create_connection
Create a Serial, TcpClient, TcpServer, Udp or SeggerRtt profile with SF defaults for omitted settings. Default COM1, 115200, 8-N-1, flow control Off, manual RTS/DTR false. Choose the actual port before connecting.
Permission: Hardware control
Parameters: name (required unique string); connect (optional boolean, false); port (string), baud_rate (positive integer), data_bits (5–8), parity (None, Odd, Even, Mark, Space), stop_bits (1, 1.5, 2), flow_control (Off, Manual, HardwareRtsCts, SoftwareXonXoff, Rs485Rts; aliases none, rts_cts, xon_xoff, rs485_rts), dtr and rts (booleans for manual line settings). All optional.
Network and RTT connection parameters
type: Serial (default), TcpClient, TcpServer, Udp or SeggerRtt. TCP client: host (default 127.0.0.1), network_port (default 19021). TCP server: local_port (default 5000). UDP: local_port (5001), remote_address (127.0.0.1), remote_port (5000), broadcast (false). Ports are integers 1–65535. Serial port remains a COM string; network_port is separate. Only fields appropriate to the transport are accepted. TCP server binds all IPv4 interfaces; UDP uses SF's existing local binding. Use a trusted network and firewall. A listening TCP server may have no connected peer. Existing connection types cannot be changed; create a new profile instead. RTT: type SeggerRtt (alias rtt), host (default 127.0.0.1), network_port (default 19021). Start the J-Link RTT Telnet endpoint separately, with the target firmware running and RTT initialized. SF does not select the probe, MCU, debug interface, speed or channel through this API. Profiles sharing an RTT endpoint may reuse the same SF transport; use a single profile for isolated testing.

Data transmission and reception
Use an open connection and firmware-specific commands. Direct send/query supports 1–4096 bytes. No newline is appended automatically. Each connection has a 64 KiB MCP receive buffer; reading does not consume it. ASCII output is a convenience representation; use HEX for binary fidelity.
sf_send
Transmit bytes once. Does not wait for a reply.
Permission: Hardware control
Parameters: id (required string): connection name or unique ID. data (required string); format (required: ascii, hex, binary); interpret_escapes (optional boolean, true; ASCII only). HEX accepts whitespace; binary uses space-separated eight-bit groups.
Example arguments
{
  "id": "Default",
  "data": "version ?\\r\\n",
  "format": "ascii"
}
Response: id, sent (byte count).
sf_receive
Read oldest buffered bytes without removing them. Repeated calls can return the same bytes.
Permission: Bridge enabled
Parameters: id (required string): connection name or unique ID. max_bytes (required integer; clamped to 1–65536).
Example arguments
{
  "id": "Default",
  "max_bytes": 1024
}
Response: id, hex, ascii, count, buffered, dropped, destructive=false.
sf_clear_receive
Clear only the selected MCP receive buffer and dropped counter; does not clear the SF GUI log.
Permission: Hardware control
Parameters: id (required string): connection name or unique ID.
Example arguments
{
  "id": "Default"
}
Response: id, cleared.
sf_query
Clear the selected MCP buffer, transmit once, wait the full collection interval, then return buffered bytes. Unsolicited traffic may be included; this is not a protocol-specific reply matcher.
Permission: Hardware control
Parameters: id (required string): connection name or unique ID. data (required string); format (required: ascii, hex, binary); interpret_escapes (optional boolean, true; ASCII only). HEX accepts whitespace; binary uses space-separated eight-bit groups. timeout_ms (optional integer, default 1000; clamped 1–20000).
Example arguments
{
  "id": "Default",
  "data": "version ?\\r\\n",
  "format": "ascii",
  "timeout_ms": 1000
}
Response: id, ascii, hex, count, timed_out (true if no bytes), dropped.

Watch fresh incoming bytes for the configured raw pattern without consuming the MCP buffer. Does not itself send an answer or command. Existing active SF rules may still act independently. Only one bridge request is processed at a time; do not expect another MCP send to run concurrently.
Permission: Bridge enabled

}
Response: matched, timed_out; on match hex and ascii. May fail if connection closes or wait buffer overflows.
Data formats and escapes
For direct ASCII send/query, interpret_escapes defaults to true. In a plain Inspector data field type version?\r\n (one backslash per escape). In JSON mode type "version?\\r\\n" as shown in the examples; JSON decoding removes one level of escaping. JSON actual CR/LF escapes also work. Supported direct escapes: \r \n \t \0 \b \e \\ \xNN. Set interpret_escapes=false for literal backslashes. Sequence data uses SF's own conversion, not the Rust direct-send parser.
HEX example: 4F 4B 0D 0A. Binary example: 01001111 01001011. ASCII is not UTF-8 text transmission.
Inspector workflows
  1. Start SF, enable the bridge and required permissions. In the source tree run StartMCPInspector.bat; it builds the development executable. Connect in Inspector and list tools.
  2. Run sf_server_info, sf_list_ports and sf_list_connections. Create or configure a serial profile, then connect.
  3. For direct command/response use sf_query. For a stored sequence use sf_list_send_sequences, then sf_execute_send_sequence with id=index:55 (example index) and connection_id=Default (example connection). Do not reverse these fields. Read the response with sf_receive and max_bytes=1024. Clear the MCP buffer before sending if you need only fresh data.
  4. To wait for unsolicited traffic, use sf_wait_receive_sequence. A timeout is not proof the device failed; check the pattern, port and timing.
  5. Use sf_project_info before switching projects. Save changes explicitly.
Permissions and safety
Tools → MCP Server Settings controls the bridge, hardware control, project management, project saving, sequence editing, sequence execution and activity logging. Read-only does not automatically disable independently enabled project or editing permissions. Active receive rules with automatic answers or stop actions require hardware and execution permissions when edited. Enable only what a trusted client needs. Hardware commands can change device state; verify the target before transmitting. Do not blindly retry timed-out writes.
Troubleshooting and security
If the bridge is disconnected, check SF is running under the same Windows account, MCP is enabled, and SF is compatible. Use sf_server_info and sf_list_connections first. For hardware operations enable hardware control only for trusted clients. Do not automatically retry timed-out writes. Close all MCP clients before upgrading or uninstalling. No network port is needed for the MCP bridge itself; RTT requires a running RTT Telnet endpoint.
